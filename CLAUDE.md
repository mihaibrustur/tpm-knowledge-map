# TPM Knowledge Map: project context

"Behind the Delivery": the owner's professional portfolio (home page, case studies) plus an interactive map of technical program management knowledge. Static site (HTML, CSS, vanilla JS, D3 from a CDN), generated by `build.js`, hosted on GitHub Pages.

## Files
- `tpm-knowledge`: git-ignored symlink to the notes folder in the owner's Obsidian vault. All content lives there as markdown, one file per node (format in its README). Edit notes there, not in the repo.
- `build.js`: compiles `tpm-knowledge/` into `data.js`, then calls `site.js` (`node build.js`). Never edit `data.js` or the generated pages by hand; rebuild and commit them.
- `site.js`, `site.css`: generate and style the portfolio pages: `index.html` (home), `work/` (case studies from `tpm-knowledge/case-studies/`), `sitemap.xml`. Only `status: published` case studies are built; `node build.js --drafts` adds drafts for local preview, and `check-names.sh` refuses to pass while a draft page exists.
- `data.js`: generated `window.TPM_DATA.nodes`, loaded by the site.
- `app.js`: force graph, drill-down, side panel, search, revisit tracking (localStorage).
- `map/index.html`, `styles.css`: the knowledge map page and its theming (dark only, styled after a space-strategy sensors view). Old `/#node-id` links redirect to `map/#node-id`.
- `check-names.sh`: fails if any term in the local, git-ignored `.banned-terms` appears in site files.

## Hard rules
- The repo is public. Never write company, client, colleague or identifying product names in any file, including this one, commit messages and code comments. Employers are described by type ("a cybersecurity scale-up"). The owner's own name, LinkedIn and email may appear on the site.
- Avoid indirect identifiers too (distinctive project names, very specific numbers, dates, locations).
- Run `./check-names.sh` before every commit or push.

## Content conventions
- Node types: `domain` (a folder's `index.md`), `concept` (a file in a domain folder, which is its `parent`), `story` (in `stories/`). The id is the file name. Links come from `parent` and `related`.
- `author`: `ai` for text drafted by Claude, `mine` once the owner has written or rewritten it. Be explicit about which is which; never mark AI text as `mine`.
- Stories have an empty `## Experience` section until the owner writes them. Do not invent experience. Interview the owner, keep it anonymous, then fill `experience`.

## Working style
- The owner wants to learn or revisit concepts while building. Explain a concept briefly when adding or editing it, and pressure-test ideas instead of validating automatically. Acknowledge trade-offs rather than calling choices "the best".
- Keep writing calm, clear and simple. No corporate fluff or heavy frameworks.
- The owner keeps a private writing-voice guide at `writing/how-i-write.md`, in the same vault as the `tpm-knowledge` folder. Follow it when refining dictation, and update it after each story: add voice traits you notice, record every correction the owner makes to a draft under "What my corrections taught", and add a line to its change log. Never copy it into this repo.
